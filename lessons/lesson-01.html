강체 변환과 좌표계

SLAM이 하는 일을 한 문장으로 줄이면 로봇이 지금 어디에 있고 어느 쪽을 보는지, 즉 pose를 계속 추정하는 일로 요약됨. pose는 회전과 이동으로 이루어지고, 둘을 합친 것을 강체 변환이라 부름. 이 강의에서는 앞으로 열네 강 동안 매번 쓰일 언어를 익힘. 여기서 표기법과 해석을 정확히 잡아 두면, 뒤에서 수식이 길어져도 헤매지 않게 됨.

이 강의를 마치면
  • 회전 행렬의 각 숫자가 무엇을 뜻하는지 그림으로 설명할 수 있음
  • Twc 같은 표기를 보고 어느 좌표계에서 어느 좌표계로 가는지 바로 읽음
  • 변환을 이어 붙이고 뒤집는 계산을 손과 코드로 틀리지 않고 함
  • 두 시점의 pose로 상대 이동(오도메트리)을 구함
  • ROS tf, Eigen, ORB-SLAM이 각각 어떤 규약을 쓰는지 앎
준비물

행렬 곱셈, 삼각함수(sin, cos). 벡터의 내적과 외적은 2절에서 복습함.

예상 시간

읽기 1시간 30분, 예제와 코드 1시간, 연습문제 40분

월드(map)에서 본 점 p

실험실: 슬라이더를 움직이면 그림과 행렬이 함께 바뀜. 처음 값은 10절의 예제와 같음. 축 색은 rviz와 같게 x는 빨강, y는 초록으로 표시함. 본문을 읽다가 "이 행렬의 첫 열이 뭐였지?" 싶을 때마다 여기로 돌아와 값을 바꿔 볼 것.

1. 왜 이걸 제일 먼저 배우나

pose는 두 가지로 이루어짐.

  • 회전(rotation): 어느 방향을 보고 있는가. 3D에서 자유도 3개(roll, pitch, yaw)
  • 이동(translation): 어디에 있는가. 3D에서 자유도 3개(x, y, z)

그래서 3D 공간에서 강체의 pose는 자유도가 6개이고, 흔히 "6-DoF pose"라고 부름. 평지를 주행하는 바퀴형 AMR은 x, y, yaw 세 개만 신경 쓰면 되지만, 카메라는 로봇이 기울거나 흔들릴 때 6개가 모두 움직임. Visual SLAM이 2D LiDAR SLAM보다 수학이 무거운 첫 번째 이유가 여기에 있음.

ROS를 써 봤다면 이 개념을 이미 매일 쓰고 있었던 것과 같음. ROS의 tf 트리 map → odom → base_link → laser에서 화살표 하나하나가 강체 변환에 해당함. slam_toolbox가 하는 일도 결국 "레이저 스캔이 지도에 가장 잘 맞도록 map → base_link 변환을 고르는 것"으로 볼 수 있음. 이번 강의에서는 그걸 수식으로 정확히 이해해 봄.

강체 변환이 Visual SLAM 파이프라인의 어디서 나오는지 미리 보면 동기가 생김.

투영지도의 3D 점을 카메라 좌표로 옮긴 뒤 이미지에 찍음 (Tcw)6강
두 프레임 사이 움직임특징점 매칭으로 카메라가 얼마나 움직였는지 구함 (Tc1c2)8, 9강

2. 벡터와 좌표계 기초

점과 벡터는 다름

둘 다 숫자 세 개로 쓰지만 의미가 다름.

  • 점(point): 공간의 한 위치. 예: 컵이 놓인 곳, 맵의 랜드마크
  • 벡터(vector): 방향과 크기만 있고 위치가 없는 것. 예: 속도, 로봇이 바라보는 방향, 두 점 사이의 차이

이 구분이 중요한 이유: 좌표계를 옮길 때 둘이 다르게 움직임. 좌표계를 평행이동하면 점의 좌표는 바뀌지만, 속도 벡터는 변하지 않음. 로봇이 북쪽으로 1m/s로 달린다는 사실은 원점을 어디에 두든 변하지 않으니까. 회전은 둘 다에 영향을 줌. 8절의 동차 좌표에서 이 차이를 숫자 하나(마지막 성분 1 또는 0)로 표현하게 됨.

좌표는 기저에 대한 성분

좌표계는 원점 하나와 서로 수직인 단위벡터 세 개(기저, basis) ex, ey, ez로 정해짐. 점 p의 좌표 (a, b, c)는 "원점에서 출발해 ex 방향으로 a, ey 방향으로 b, ez 방향으로 c만큼 가면 p에 닿는다"는 뜻으로 읽음.

p = a·e_x + b·e_y + c·e_z

같은 점이라도 기저가 다르면 성분이 달라짐. 로봇 바로 앞 1m의 컵은 로봇 좌표계에서 (1, 0, 0)이지만, 월드 좌표계에서는 로봇이 서 있는 위치와 방향에 따라 (5, 3, 0)일 수도 (-2, 7, 0)일 수도 있음. 강체 변환은 "같은 점의 성분을 한 기저에서 다른 기저로 바꿔 쓰는 규칙"이라고 이해하면 됨.

오른손 좌표계

로보틱스는 거의 예외 없이 오른손 좌표계를 씀. 오른손 엄지를 x, 검지를 y로 펴면 중지가 가리키는 방향이 z가 됨. 다르게 말하면 x에서 y로 돌리는 방향으로 오른손을 감쌌을 때 엄지가 z를 가리킴. 이 규칙 덕분에 "z축 기준 +90° 회전"이 위에서 내려다볼 때 반시계 방향이라는 것이 정해짐. ROS에서 왼쪽으로 도는 yaw가 양수가 되는 것도 이 규칙을 따름.

내적과 외적 복습

  • 내적 a·b = |a||b|cosθ. 단위벡터끼리의 내적은 두 방향이 얼마나 같은지를 나타냄. 같으면 1, 수직이면 0, 반대면 -1. 그리고 단위벡터 e와의 내적은 "e 방향 성분"을 뜻함. 4절에서 이 성질로 회전 행렬을 만듦.
  • 외적 a×b는 a와 b에 동시에 수직인 벡터이고, 크기는 |a||b|sinθ, 방향은 오른손 법칙을 따름. 오른손 좌표계에서는 ex × ey = ez가 성립함. 3강에서 회전의 미분을 다룰 때 외적이 다시 나옴.

함정: 광학 좌표계는 축이 다름

카메라 영상의 픽셀 좌표는 왼쪽 위가 원점이고 u는 오른쪽, v는 아래로 커짐. 광학 좌표계는 이 픽셀 방향에 맞춰 x를 오른쪽, y를 아래로 잡고, 그러면 오른손 법칙에 의해 z가 앞(카메라가 보는 방향)이 됨. 로봇 몸체 좌표계와 축 이름이 서로 엇갈려 있음.

둘 다 카메라 바로 뒤에서 카메라가 보는 방향으로 바라본 모습. ⊗ 표시는 화면 안쪽을 향하는 축을 뜻함.

두 좌표계 사이의 회전은 고정된 행렬 하나로 표현됨. 4절의 "열 = 축" 규칙으로 직접 만들어 보면 이렇게 됨. 광학 x(오른쪽)는 몸체 좌표로 -y, 광학 y(아래)는 -z, 광학 z(앞)는 +x에 해당함.

R_link_optical = [  0    0    1 ]
                 [ -1    0    0 ]
                 [  0   -1    0 ]

열1 = 광학 x를 몸체 좌표로 = (0, -1,  0)   오른쪽 = -y
열2 = 광학 y를 몸체 좌표로 = (0,  0, -1)   아래   = -z

현장에서 실제로 나는 버그: RealSense 같은 드라이버는 camera_link와 camera_color_optical_frame을 둘 다 퍼블리시함. 포인트클라우드나 특징점이 어느 프레임 기준인지(header.frame_id) 확인하지 않고 쓰면, 점들이 90° 돌아간 채로 지도에 찍힘. 이 행렬이 빠졌을 때 나타나는 전형적인 증상.

4. 회전 행렬

2D에서 직접 유도하기

공식을 외우지 말고 만들어 볼 것. 월드 좌표계 w에 대해 θ만큼 돌아간 로봇 좌표계 b가 있음. b의 기저벡터를 w에서 보면 이러함.

b의 x축 = ( cosθ, sinθ )      ← 각도 θ 방향의 단위벡터
b의 y축 = (-sinθ, cosθ )      ← 거기서 90° 더 돈 방향

b 좌표계에서 (a, b)인 점은 정의상 "b의 x축으로 a, b의 y축으로 b만큼 간 곳"이므로, w 좌표로는

p_w = a·(cosθ, sinθ) + b·(-sinθ, cosθ)

    = [ cosθ  -sinθ ] [a]
      [ sinθ   cosθ ] [b]   = R(θ) · p_b

행렬의 첫 열은 b의 x축, 둘째 열은 b의 y축이 됨. 공식을 잊어도 "열에 새 축을 세워 넣는다"만 기억하면 언제든 다시 만들 수 있음.

확인 하나. 점 (1, 0)을 90° 돌리면 cos90° = 0, sin90° = 1이므로

[ 0  -1 ] [1]   [0]
[ 1   0 ] [0] = [1]

x축 위의 점이 y축으로 돌아갔으니 맞음.

3D에서: 열이 곧 축

이 강의에서 가장 중요한 문장: 회전 행렬 Rwb의 각 열은 b 좌표계의 x, y, z축을 w 좌표계에서 본 방향 벡터를 담고 있음. 첫 열을 보면 로봇의 앞 방향이 월드에서 어디를 가리키는지, 셋째 열을 보면 로봇의 위 방향이 어디를 가리키는지 알 수 있음.
R_wb = [ x_b  y_b  z_b ]   (각 열이 w에서 본 b의 축)

2절의 내적 성질을 쓰면 원소 하나하나의 의미도 나옴. R의 (i, j) 원소는 w의 i번째 축과 b의 j번째 축의 내적, 즉 두 축 사이 각도의 코사인과 같음. 그래서 회전 행렬을 방향 코사인 행렬(Direction Cosine Matrix, DCM)이라고도 부름. 항공 쪽 문헌에서 DCM이라는 말이 나오면 같은 대상을 가리킴.

실험실 그림의 Twb 행렬에서 왼쪽 위 2×2의 첫 열을 볼 것. yaw를 바꾸면 그 열이 로봇의 빨간 x축 방향과 똑같이 움직임.

기본 회전 세 가지

한 축을 기준으로 도는 회전은 그 축 성분을 그대로 두고 나머지 두 성분만 2D처럼 돌림.

Rx(α) = [ 1    0      0   ]   Ry(β) = [  cosβ  0  sinβ ]   Rz(γ) = [ cosγ  -sinγ  0 ]
        [ 0  cosα  -sinα  ]           [   0    1   0   ]           [ sinγ   cosγ  0 ]
        [ 0  sinα   cosα  ]           [ -sinβ  0  cosβ ]           [  0      0    1 ]
Ry만 부호 위치가 다름: Rx와 Rz는 -sin이 오른쪽 위에 있는데 Ry는 왼쪽 아래에 있음. 실수가 아님. 오른손 법칙에서 y축 기준 회전은 z에서 x로 도는 방향(z → x)이라 순서가 뒤집혀 보임. 시험 삼아 Ry(90°)를 ez = (0, 0, 1)에 곱해 보면 (1, 0, 0)이 나옴. z축이 x축으로 돌아갔음.

회전 행렬의 성질

  1. RᵀR = I. 열벡터들이 서로 수직인 단위벡터라서 성립함. 그래서 역행렬이 그냥 전치 Rᵀ이고, 계산이 아주 쌈. 왜 그런지는 연습문제 1번에서 직접 설명해 볼 것.
  2. det(R) = +1. 오른손 좌표계를 오른손 좌표계로 보낸다는 의미를 가짐. -1이면 회전이 아니라 거울 반사(왼손 좌표계로 바뀜)가 됨.
  3. 길이와 각도 보존. 회전시켜도 벡터의 길이와 두 벡터 사이 각도는 변하지 않음. "강체(rigid body)"라는 말도 여기서 나옴.
  4. 1과 2를 만족하는 3×3 행렬의 집합을 SO(3)(Special Orthogonal group, 특수 직교군)라고 함. 3강에서 본격적으로 다룸.

숫자 9개, 자유도 3개

회전 행렬에는 숫자가 9개 있지만 RᵀR = I가 제약 6개를 걸기 때문에 실제로 자유롭게 정할 수 있는 건 3개밖에 없음. 이게 실무에서 문제가 됨. 최적화 알고리즘이 9개 숫자를 각각 조금씩 고치면, 고친 결과가 더 이상 회전 행렬이 아니게 됨(열이 서로 수직이 아니게 됨). 수치 오차가 쌓여도 같은 일이 생김. 이 문제를 푸는 방법은 2강(쿼터니언)과 3강(리 대수)에서 다룸.

5. 회전의 두 가지 해석: 능동과 수동

같은 행렬 R(90°)를 두 가지로 읽을 수 있고, 이걸 섞으면 부호가 뒤집히는 버그가 남.

  • 능동(active) 해석: 좌표계는 그대로 두고, 점이나 물체를 실제로 돌림. "점 (1, 0)을 90° 돌리면 (0, 1)이 된다."
  • 수동(passive) 해석: 점은 그대로 두고, 그 점을 보는 좌표계를 바꿈. "90° 돌아간 로봇 좌표계에서 (1, 0)인 점은 월드 좌표계에서 (0, 1)이다."

계산은 똑같지만 의미가 다름. 이 강의와 SLAM 문헌 대부분은 수동 해석을 씀. Rwb는 "b 좌표를 w 좌표로 바꿔 쓰는 행렬"로 읽음. 로봇이 실제로 무언가를 돌리는 게 아니라, 같은 점을 다른 관점에서 다시 적는 작업에 가까움.

헷갈릴 때 쓰는 질문: "지금 바뀌는 게 점인가, 관점인가?" 점이 움직이는 상황(물체 회전, 애니메이션)이면 능동, 센서가 본 걸 지도에 옮기는 상황이면 수동에 해당함. 능동으로 "좌표계를 θ만큼 돌린다"와 수동으로 "점을 본다"는 서로 역회전(Rᵀ) 관계를 이룸.

6. 회전을 이어 붙이기

순서가 결과를 바꿈

책 한 권을 들고 직접 해 볼 것. x축으로 90° 돌린 뒤 z축으로 90° 돌린 결과와, z축으로 먼저 돌린 뒤 x축으로 돌린 결과가 다름. 숫자로도 확인해 볼 것.

Rx(90°) = [ 1  0   0 ]     Rz(90°) = [ 0  -1  0 ]
          [ 0  0  -1 ]               [ 1   0  0 ]
          [ 0  1   0 ]               [ 0   0  1 ]

e_x = (1, 0, 0)에 적용하면:
  Rz·Rx·e_x :  Rx·e_x = (1, 0, 0)  →  Rz·(1, 0, 0) = (0, 1, 0)
  Rx·Rz·e_x :  Rz·e_x = (0, 1, 0)  →  Rx·(0, 1, 0) = (0, 0, 1)

결과가 하나는 y축, 하나는 z축으로 나옴. 행렬 곱은 교환법칙이 성립하지 않고, 회전도 마찬가지로 순서를 바꾸면 결과가 달라짐. 2D 회전(z축 하나만 도는 경우)은 예외적으로 순서와 상관없는데, 그래서 평지를 다니는 2D 로봇만 다룰 때는 이 문제가 잘 드러나지 않음.

고정축 기준과 현재축 기준

R1을 한 다음 R2를 한다고 할 때, 곱하는 방향은 "R2를 어느 축 기준으로 하느냐"에 따라 다름.

두 번째 회전의 기준곱하는 방법예
처음의 고정된 축 (월드 축)왼쪽에 곱함: R2·R1"지도 기준으로 북쪽을 향해 돌려라"
이미 돌아간 현재 축 (몸체 축)오른쪽에 곱함: R1·R2"지금 보는 방향에서 고개를 들어라"

드론이나 카메라의 roll-pitch-yaw는 보통 몸체 축 기준으로 정의되어 R = Rz(yaw)·Ry(pitch)·Rx(roll)처럼 쓰임. 2강에서 오일러각을 다룰 때 이 규칙이 그대로 쓰임.

7. 강체 변환과 표기법

회전에 이동을 더하면 강체 변환이 됨. 카메라 좌표계의 점 pc를 월드 좌표계로 옮기는 공식은 이러함.

p_w = R_wc · p_c + t_wc

먼저 회전으로 축 방향을 월드에 맞추고, 그다음 카메라가 있는 위치만큼 옮김. 순서를 바꿔 "먼저 옮기고 돌리면" 결과가 달라지니 주의할 것.

이 강의의 표기 규칙 (Visual SLAM 14강, Barfoot 책과 같음): Twc는 c 좌표계의 좌표를 w 좌표계의 좌표로 바꾸는 변환을 뜻함. 아래첨자를 오른쪽에서 왼쪽으로, c → w로 읽음. twc는 월드에서 본 카메라의 위치이기도 함. 카메라 원점 (0, 0, 0)을 넣으면 pw = twc가 나옴. 그래서 Twc를 "월드에서 본 카메라의 pose"라고 부름.

이 표기를 쓰면 변환을 이어 붙일 때 안쪽 첨자가 맞물려 사라짐. 첨자가 맞물리지 않는 식(Twb·Tcb 같은)이 보이면 그 자체로 버그 신호로 봐야 함.

T_wc = T_wb · T_bc          (b끼리 맞물림  ✓)
T_wc = T_wb · T_cb          (b와 c가 안 맞음 ✗ → T_cb를 뒤집어야 함)

라이브러리마다 규약이 다름

실무에서 시간이 가장 많이 새는 부분이기도 함. 코드를 읽기 전에 그 라이브러리가 무엇을 저장하는지부터 확인할 것.

도구무엇을 쓰나주의할 점
ROS tf2lookupTransform(target, source)는 source 좌표를 target 좌표로 바꾸는 변환, 즉 Ttarget,source를 돌려줌lookupTransform("map", "base_link")는 Tmap,base = 맵에서 본 로봇 pose
ORB-SLAM2/3프레임과 키프레임에 주로 Tcw(월드 → 카메라)를 저장함카메라 위치가 필요하면 역변환해서 Twc의 이동 부분을 꺼내야 함. Tcw의 이동 부분은 카메라 위치가 아님
EigenIsometry3d는 그냥 4×4 변환이고, 의미는 변수 이름으로 정함변수 이름에 T_wc처럼 첨자를 꼭 붙이는 습관을 들일 것
KITTI, TUM 데이터셋정답 궤적은 카메라 pose Twc 형태TUM은 쿼터니언 순서가 qx qy qz qw (2강에서 다룸)

8. 동차 좌표

왜 필요한가

R·p + t는 곱셈 뒤에 덧셈이 붙어서, 두 번만 이어 붙여도 식이 지저분해짐.

p_w = R_wb (R_bc p_c + t_bc) + t_wb
    = (R_wb R_bc) p_c + (R_wb t_bc + t_wb)

세 번, 네 번 이어 붙이면 손으로 따라가기 힘들어짐. 그래서 점 뒤에 1을 붙여 차원을 하나 늘리고, 회전과 이동을 4×4 행렬 하나로 묶음.

T = [ R   t ]      p̃ = [ p ]      T·p̃ = [ R·p + t ]
    [ 0ᵀ  1 ]          [ 1 ]             [    1    ]

이제 변환을 이어 붙이는 일이 그냥 행렬 곱셈으로 끝남. 위의 두 단계 식을 4×4로 곱해 보면 정확히 같은 결과가 나옴. 이런 4×4 행렬의 집합을 SE(3)(Special Euclidean group, 특수 유클리드 군)라고 부름.

마지막 성분 1과 0

2절에서 점과 벡터는 다르다고 했음. 동차 좌표에서 그 차이가 마지막 성분으로 드러남.

점:    [x, y, z, 1]  →  T를 곱하면 회전과 이동이 모두 적용됨
방향:  [x, y, z, 0]  →  T를 곱하면 회전만 적용됨 (t에 0이 곱해짐)

로봇의 속도나 법선 벡터를 다른 좌표계로 옮길 때 실수로 이동까지 더하는 버그를, 이 규칙 하나로 막을 수 있음.

역변환 유도

pw = R·pc + t를 pc에 대해 풀면 됨. 양변에서 t를 빼고 Rᵀ를 곱함(Rᵀ = R⁻¹이므로).

p_w − t   = R · p_c
Rᵀ(p_w − t) = p_c
p_c = Rᵀ·p_w − Rᵀ·t

T⁻¹ = [ Rᵀ   -Rᵀ·t ]
      [ 0ᵀ     1   ]

Twc를 알면 Tcw = Twc⁻¹이고, 이걸로 맵의 3D 점을 카메라 좌표로 가져옴. 6강에서 점을 이미지에 투영할 때 매번 이 계산을 씀. 일반 4×4 역행렬(np.linalg.inv)로도 계산은 되지만, 이 공식이 훨씬 빠르고 수치적으로도 안정적이라 이쪽을 씀.

여기서 많이 틀림: 역변환의 이동 부분은 -t가 아니라 -Rᵀ·t가 됨. 회전을 거꾸로 했으면 이동도 거꾸로 된 회전을 거쳐야 함.

9. 상대 pose: 오도메트리의 정체

SLAM에서는 두 시점 사이에 로봇이 얼마나 움직였는지를 가장 자주 계산함. 시각 1과 2의 pose Tw1, Tw2를 알 때, 시각 1의 로봇이 본 시각 2의 로봇 pose는

T_12 = T_1w · T_w2 = T_w1⁻¹ · T_w2

첨자가 1 ← w ← 2로 맞물림. 거꾸로, 상대 이동 T12를 알면 다음 pose를 Tw2 = Tw1·T12로 구함. 휠 오도메트리, VO, LiDAR 스캔 매칭이 하는 일이 모두 T12를 구해서 이렇게 계속 곱해 나가는 방식으로 동작함. 곱할 때마다 작은 오차도 같이 곱해지므로 오차가 쌓이는데, 이것이 드리프트이고 13강의 루프 클로저가 이 문제를 풂.

예제: 두 pose 사이의 상대 이동

로봇이 시각 1에 (2, 1)에서 yaw 90°, 시각 2에 (2, 3)에서 yaw 180°였음. 시각 1의 로봇 입장에서 시각 2의 로봇은 어디에 있을까?

T_1w = T_w1⁻¹ :  Rᵀ = R(-90°) = [  0  1 ]     -Rᵀ·t = -[  0  1 ][2] = -( 1) = (-1)
                               [ -1  0 ]              [ -1  0 ][1]    (-2)   ( 2)

T_12 = T_1w · T_w2
  회전:  R(-90°)·R(180°) = R(90°)
  이동:  R(-90°)·(2, 3) + (-1, 2) = (3, -2) + (-1, 2) = (2, 0)

시각 1의 로봇 기준으로 시각 2의 로봇은 정면 2m 앞에 있고, 왼쪽으로 90° 돌아 있음. 그림으로 확인해 보면, (2, 1)에서 +y를 보던 로봇이 2m 직진해 (2, 3)에 갔고, 방향이 90°에서 180°로 바뀌었으니 맞음.

10. 손으로 풀어보는 예제

상황: 로봇이 월드 좌표 (2, 1)에 서서 yaw 90°로 +y 방향을 봄. 카메라는 로봇 앞 0.5m에 같은 방향으로 달려 있음(여기서는 optical frame을 무시하고 카메라도 x가 앞이라고 함). 카메라가 정면 1m에 장애물을 봤음. pc = (1, 0, 0). 장애물의 월드 좌표는?

1단계, 카메라 → 로봇: Rbc = I, tbc = (0.5, 0, 0)이므로 pb = (1, 0, 0) + (0.5, 0, 0) = (1.5, 0, 0)

2단계, 로봇 → 월드: Rwb = R(90°), twb = (2, 1, 0)

R(90°)·(1.5, 0) = (0·1.5 − 1·0,  1·1.5 + 0·0) = (0, 1.5)
p_w = (0, 1.5) + (2, 1) = (2, 2.5)

검산: 로봇이 (2, 1)에서 +y를 보고 있고 장애물이 정면 1.5m에 있으니 (2, 2.5)가 맞음. 실험실 그림의 처음 값도 이 예제와 같음.

한 걸음 더: 실제 카메라라면 pc는 광학 좌표계로 나옴. 정면 1m는 광학 좌표로 (0, 0, 1)이 됨. 3절의 Rlink,optical을 곱하면 (1, 0, 0)이 되어 위 계산과 이어짐. 실제 시스템에서는 Twc = Twb·Tb,link·Tlink,optical처럼 한 단계가 더 붙는다는 것만 기억할 것.

숫자를 넣고 그림으로 봐도 말이 되는지 확인하는 습관이 SLAM 디버깅의 절반은 해결됨.

11. 코드로 확인하기

Python (numpy, 3D)

import numpy as np

def Rz(deg):
    t = np.deg2rad(deg)
    return np.array([[np.cos(t), -np.sin(t), 0],
                     [np.sin(t),  np.cos(t), 0],
                     [0,          0,         1]])

def make_T(R, t):
    T = np.eye(4)
    T[:3, :3] = R
    T[:3, 3] = t
    return T

def inv_T(T):                      # 8절의 공식 그대로
    R, t = T[:3, :3], T[:3, 3]
    return make_T(R.T, -R.T @ t)

T_wb = make_T(Rz(90), [2, 1, 0])
T_bc = make_T(np.eye(3), [0.5, 0, 0])
T_wc = T_wb @ T_bc                 # 첨자 b가 맞물림

p_c = np.array([1, 0, 0, 1])       # 점: 마지막 성분 1
print(T_wc @ p_c)                  # → [2.  2.5 0.  1. ]

v_c = np.array([1, 0, 0, 0])       # 방향: 마지막 성분 0
print(T_wc @ v_c)                  # → [0. 1. 0. 0.]  이동이 안 붙음

# 검증 습관: 회전 행렬이 맞는지, 역변환이 맞는지 확인
R = T_wc[:3, :3]
assert np.allclose(R.T @ R, np.eye(3)) and np.isclose(np.linalg.det(R), 1)
assert np.allclose(inv_T(T_wc) @ T_wc, np.eye(4))

C++ (Eigen)

ORB-SLAM, VINS 같은 실제 SLAM 코드는 대부분 C++과 Eigen으로 작성되어 있음. 같은 계산을 Eigen으로 쓰면 이러함.

#include <Eigen/Geometry>
#include <iostream>

int main() {
  Eigen::Isometry3d T_wb = Eigen::Isometry3d::Identity();
  T_wb.rotate(Eigen::AngleAxisd(M_PI / 2, Eigen::Vector3d::UnitZ()));
  T_wb.pretranslate(Eigen::Vector3d(2, 1, 0));   // T = 이동 · 회전

  Eigen::Isometry3d T_bc = Eigen::Isometry3d::Identity();
  T_bc.pretranslate(Eigen::Vector3d(0.5, 0, 0));

  Eigen::Isometry3d T_wc = T_wb * T_bc;
  Eigen::Vector3d p_c(1, 0, 0);
  std::cout << (T_wc * p_c).transpose() << std::endl;      // 2 2.5 0

  Eigen::Isometry3d T_cw = T_wc.inverse();       // Isometry는 Rᵀ 공식을 씀
  std::cout << T_cw.translation().transpose() << std::endl;
}
Eigen 함정: rotate()는 오른쪽에, pretranslate()는 왼쪽에 곱함. translate()(오른쪽에 곱함)와 헷갈리면 "회전된 축 방향으로 이동"이 되어 결과가 달라짐. 6절의 고정축/현재축 규칙과 같은 원리가 적용됨.

12. 디버깅 체크리스트

좌표 변환 버그는 에러 메시지 없이 틀린 값만 냄. 결과가 이상하면 이 순서로 확인할 것.

증상의심할 것
점들이 거울에 비친 듯 뒤집힘T와 T⁻¹을 바꿔 씀, 또는 det(R) = -1인 행렬
점들이 90° 돌아간 채로 찍힘광학 좌표계와 몸체 좌표계 혼동
회전은 맞는데 위치가 조금씩 어긋남역변환 이동 부분을 -t로 씀, 또는 곱셈 순서
로봇이 돌 때만 오차가 커짐센서 장착 위치(extrinsic)의 이동 부분이 틀림
값이 약 57배 차이 남도(degree)와 라디안 혼동 (1 rad ≈ 57.3°)
시간이 지날수록 회전 행렬이 이상해짐수치 오차 누적으로 직교성이 깨짐. 주기적으로 재직교화하거나 쿼터니언을 씀

13. 핵심 정리

  1. pose = 회전 + 이동 = 강체 변환. 3D에서 자유도 6개
  2. 점은 이동의 영향을 받고 방향 벡터는 받지 않음. 동차 좌표의 마지막 성분 1과 0이 이 차이를 표현함
  3. 회전 행렬의 열은 회전된 축의 방향을 나타냄. 역행렬은 전치이고, 집합 이름은 SO(3)
  4. SLAM은 수동 해석을 씀. Rwb는 점을 돌리는 게 아니라 b 좌표를 w 좌표로 다시 쓰는 것
  5. 회전은 순서가 중요함. 고정축 기준이면 왼쪽에, 현재축 기준이면 오른쪽에 곱함
  6. Twc는 c → w. 첨자를 오른쪽에서 왼쪽으로 읽고, 이어 붙일 때 안쪽 첨자가 맞물림
  7. 역변환의 이동 부분은 -Rᵀt
  8. 상대 pose T12 = Tw1⁻¹·Tw2. 오도메트리는 이걸 계속 곱해 나가는 것이고, 그래서 드리프트가 생김
  9. 라이브러리마다 규약이 다름. tf2는 Ttarget,source, ORB-SLAM은 Tcw를 주로 저장함

문제 1 · 개념

회전 행렬의 역행렬이 왜 전치행렬과 같은지, 열이 회전된 축의 방향이라는 해석으로 직관적으로 설명해 볼 것. 힌트: RᵀR의 (i, j) 원소는 R의 i번째 열과 j번째 열의 내적과 같음. 서로 수직인 단위벡터끼리 내적하면 몇일까?

문제 2 · 계산

10절 예제의 로봇 pose(위치 (2, 1), yaw 90°)에서 월드 좌표 (3, 1)의 점은 로봇 좌표계로 어디일까? Tbw = Twb⁻¹ 공식으로 구하고, 그림으로도 맞는지 확인해 볼 것.

문제 3 · ROS 연결

Tmap,odom과 Todom,base를 알 때 Tmap,base는 어떻게 구하는가? 그리고 AMCL이나 slam_toolbox가 map → base_link가 아니라 map → odom을 퍼블리시하는 이유를 3절 표의 성질을 참고해 설명해 볼 것.

문제 4 · 함정

누군가 Twc의 역변환을 [Rᵀ, -t; 0, 1]로 구현했음. 이 코드가 우연히 맞는 결과를 내는 경우와 틀리는 경우는 각각 언제일까?

문제 5 · 도전

ORB-SLAM에서 어떤 키프레임의 Tcw가 회전 R(yaw 90°), 이동 (1, 0, 0)으로 저장되어 있음(2D로 생각해도 됨). 이 카메라의 월드 좌표상 위치는 어디인가? "이동 부분이 (1, 0, 0)이니 카메라는 (1, 0, 0)에 있다"는 답이 왜 틀렸는지도 설명해 볼 것.
